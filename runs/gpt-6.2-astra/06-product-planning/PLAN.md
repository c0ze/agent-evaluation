# Offline inspection pilot

An inspector who sees **Ready offline** before entering a basement should be able to reopen the inspection in airplane mode, finish the form, capture 40 photos and a signature, and recover each saved item after the app restarts. **Saved on tablet**, **Submitted** and **Accepted** are distinct promises. Only the server can confirm the last two.

## Decisions before implementation

Each recommendation below is a pilot assumption. The owner confirms it before work starts on the dependent feature.

| Decision and owner | Recommendation and assumption to verify |
| --- | --- |
| What counts as acceptance? Product and operations | Treat submission as delivery for review and acceptance as a terminal server transition by an authorized supervisor. An acceptance request closes new downloads and can remain pending while a tablet is away. Walk through a lost tablet and an urgent acceptance with supervisors. If acceptance must be immediate, redesign the deletion guarantee before enrolling inspections. |
| What constitutes removal and an adequate audit? Security and the regulatory owner | Obtain agreement on destruction of per-inspection encryption keys plus cleanup of files and indexes. Confirm which devices, caches, backups, audit events and historical records are in scope, what evidence proves removal, and the server audit retention period. Qualify the actual managed tablet image. |
| What can be prepared and for how long? Field operations | Preload assigned inspections on a connected tablet. Pin the form definition, references and validations needed for the visit. Agree the managed-device offline unlock period, whether delayed assignment revocation is acceptable, and the storage budget using representative jobs and full-size photos. |
| Who resolves changes, and what does signing mean? Product and inspection leads | Merge independent field edits automatically. Let an authorized reviewer resolve overlaps and record the choice. Agree on the exact fields and photo manifest the signer reviews. Any change to that content requires a new signature. Confirm this with inspectors and supervisors using a signed draft that a supervisor corrects. |
| Can every reader and writer participate? Engineering | Require tracked tablet downloads and version-checked, audited writes for pilot records, including web, administrative and older-client paths. Verify API behavior on stale writes, compatibility with pinned forms, and the ability to inventory or clean existing tablet caches before choosing the pilot cohort. |

## Field workflow and scope

1. While connected, the inspector selects assigned work to prepare. Opening an assigned inspection online also starts preparation. Enable editing once its base form is committed locally, so losing signal after opening cannot discard a saved note. Check identity, assignment and available space before download. Show progress for the form, existing answers and required media. Mark the inspection ready only after a durable, verified snapshot is available. An offline roster shows prepared assignments and identifies which others still need a download.
2. In the basement, the inspector opens the local copy. Persist note edits as they are entered, flush on navigation, and show **Saved on tablet** only after the SQLite commit. Report storage failures at the point of entry. Show a thumbnail only as saved once the photo bytes and their database reference are durable. Display the remaining photo count and permit replacement before signing.
3. Validate required fields locally, show the review copy, capture the signature and queue submission. An incomplete inspection can stay a draft. A queued submission survives restarts. Reopening it to make a correction withdraws the queued intent if it has not been sent. If delivery is uncertain, first reconcile its receipt and then create a correction against the confirmed state.
4. On reconnect, resume transfers and show outstanding photos, server receipt or **Needs review**. For a conflict, show the original answer, tablet edit and web edit. Preserve the tablet draft while the reviewer decides. If signed content changes, show **Signature needed** to the inspector. The supervisor sees the submitted revision and any tablet still blocking acceptance.
5. When work is delivered, release the tablet copy as described below. Show completion using a non-customer receipt. A reassigned user can no longer fetch a job. On reconnect, lock a revoked copy and route outstanding work to an authorized recovery reviewer under the agreed policy.

The pilot covers assigned inspections on managed tablets and edits in the existing supervisor web flow. General offline search, new inspection creation, peer-to-peer sync, character-level co-editing and automatic text merging are outside scope.

## Durable data on the tablet

Use SQLite as the source for the tablet UI from download through release. Keep a small installation ledger of opaque copy grants and pending purge acknowledgments. Put customer data in an encrypted per-inspection store so one inspection can be erased independently. Store full-resolution media in private encrypted files. The records below persist across app restarts.

| Record | Required contents and invariant |
| --- | --- |
| Inspection snapshot | Inspection and assignment IDs, copy grant, pinned schema, last acknowledged integer server version, server state, and base answers keyed by stable field ID. Keep the base seen by the editor until its edits are reconciled. |
| Local changes and outbox | Locally generated operation ID, actor, local sequence, observed base or predecessor, changed fields, original values, local capture time and delivery state. Commit the edit, its audit event and the queued work in one transaction. Recover the draft by applying pending changes to the acknowledged base. |
| Media and signature | Stable attachment ID, type, encrypted file reference, hash, size and transfer progress. A signature also references the digest of the reviewed content. Track photo removal as an explicit operation. Keep source bytes until release is safe. |
| Sync, receipts and conflicts | In-flight request identity, server receipts, remote version, conflicting fields and resolution status. Apply acknowledgments and advance the base in one transaction. A crash must leave either replayable work or a recorded receipt. |

Reserve space before capture, including temporary files and the signature. Write encrypted media to a temporary file, verify it, make the rename durable, then commit its reference. On restart, reclaim unreferenced files and flag missing or corrupt referenced files for recapture. Keep all previously saved work accessible if the next capture fails.

## REST synchronization and conflict rules

- **Prepare and refresh.** The server registers a durable grant for this tablet and inspection before sending customer bytes, including identifying roster details or thumbnails. A versioned snapshot includes the pinned schema and attachment manifest. On reconnect, authenticate, check the grant and fetch current state. Refresh the acknowledged base without overwriting pending edits. A full snapshot is sufficient for the pilot.
- **Write and replay.** Send ordered operations per inspection with a stable operation ID and an integer version precondition, for example `If-Match`. Freeze a request once sent. In one server transaction check authorization, state, version and validation, apply the patch, append an audit event, increment the version and store the receipt. For an authorized replay of the same ID and payload, return the original outcome even if the version has since advanced. Reject reuse with different content. Retain receipts while any grant can replay the operation. After grant closure, reject delayed writes. All web writers use the same version and audit rules.
- **Handle interruption.** On timeout, disconnect or transient server failure, retry the same request with capped exponential backoff and jitter. Honor server retry delays, and resume on foreground, reconnect or manual retry. Pause for reauthentication on expired credentials. Surface permission, schema and validation errors for review. A failed inspection does not block the queue for another. Continue saving tablet edits while older requests are in flight, preserving their dependency on earlier local edits.
- **Reconcile concurrent writes.** On a stale precondition, return the current version and changed field IDs since the observed base. Compare base, local and current values. Reapply independent fields with a new request ID against the current version. Treat identical intended values as satisfied and retain the audit lineage. For different edits to the same note or field, deletion versus modification, or incompatible schema changes, persist both candidates and pause the affected submission. An authorized choice records the reviewer, versions and selected value as a new version-checked operation. If another writer wins the race, reconcile again. Never replace a whole form with a stale tablet snapshot.
- **Bind and submit.** Use stable field IDs, normalized values, the schema version and an ordered manifest of attachment IDs and hashes to compute the reviewed-content digest on both platforms. Upload and verify referenced objects first. Submit the digest, signature reference and expected version in an idempotent request. The server recomputes the digest, validates the form and commits the signed revision atomically. A changed answer or manifest requires review and signing again. Subsequent signed-content edits on the web reopen the draft and invalidate eligibility for acceptance until resubmission.

## Photos and signatures in transit

Count up to 40 active photos across the inspection. The signature is a separate required object for submission. Key resumable upload sessions by inspection and attachment ID. Query received byte ranges after interruption, retry missing chunks, and verify length and hash before finalizing. Reuse a completed upload on retry. Authorize each session and keep partially uploaded objects private and unreferenced. Expire abandoned staging objects under an agreed cleanup period. If a session expires, start a new one from the durable local file.

Apply photo additions and removals to the manifest under the same version check as field changes. Distinct additions can merge within the limit. If a web edit makes the combined set exceed 40, preserve the local files and ask the reviewer which photos to retain. A draft with a missing object, a hash mismatch or a stale signature cannot be submitted.

## Security, audit and the 24-hour deadline

Bind offline access to the signed-in inspector and enrolled tablet. Use managed-device lock, hardware-backed key protection where available, encrypted transport, private capture without a camera-roll copy, and exclusion from backups, notifications, crash dumps and app-switcher previews. Hold store, journal, thumbnail, temporary-file and media keys under the same erasable per-inspection key. Validate shared-tablet sign-out and account switching. Lock queued work for authorized recovery if credentials expire while disconnected.

Use the server's UTC acceptance timestamp as the regulatory clock for the proposed workflow. A background timer or push message cannot guarantee deletion on a powered-off tablet. The pilot therefore requires evidence of removal from **every tablet that received a copy before acceptance can commit**.

1. Serialize grant issuance, the request for acceptance and final acceptance on the inspection. On an acceptance request, freeze new grants and record the candidate signed version. Keep the request pending while grants are open. Permit existing holders to reconcile outstanding edits. A content change cancels the candidate and sends the inspection back for review. Reviewers may cancel a pending request to allow preparation of a replacement tablet.
2. To release a copy, first persist a local lock on new edits and flush the outbox. Require receipts for all edits, objects and submission intents, or a recorded decision by an authorized reviewer on outstanding work. Put the grant into a durable closing state on the server to prevent further data access. Cancel or drain existing transfers and reject late callbacks for that grant. Close local readers, destroy the inspection key, and remove database files and journals, media, thumbnails, temporary files and identifying roster entries. Verify key removal and absence of customer files and index entries before sending an authenticated, idempotent release acknowledgment tied to the enrolled device and grant. After a crash, finish cleanup or replay the acknowledgment from an opaque marker. Require the grant check on every media download and resume request. A retry after release can obtain the release receipt only.
3. The server records verified release evidence per grant, then atomically confirms the approved signed version and zero outstanding grants before storing `accepted_at`. An accepted inspection cannot issue another tablet grant. A missing tablet holds acceptance open until it returns or the organization obtains approved proof of complete managed-device erasure. A queued remote-wipe command is insufficient. Test whether the business can tolerate this delay. If the proposed acceptance semantics or removal evidence are rejected, the pilot stays gated on an alternative proven to work through extended disconnection.
4. Keep an access-controlled, append-only server audit of edits from both clients, signatures and invalidations, conflicts and resolutions, submission, grants, releases and acceptance. Record actor, source, operation ID, versions, changed fields or protected revision references, device capture time and authoritative server time. Preserve protected history after local erasure. Keep access and retention for this evidence separate from operational logs.

## Migration and backfill

Add server grant, revision, receipt, attachment and audit storage first. Preserve existing inspection IDs, integer versions and REST reads. For each pilot record, seed a versioned baseline from its current state with a migration event, preserving any existing history. Record historical gaps explicitly. Verify counts, versions, form references and media hashes against the source. Make backfill restartable by inspection and baseline version, with a version check so a concurrent web edit cannot be overwritten.

Upgrade the tablet schema transactionally. Inventory old cache locations, including earlier installs that could have downloaded pilot records. Re-fetch verified server data into the new store. Reconcile any local-only content before removing the old cache. Check prior accepted records for residual data and route any overdue copy for immediate cleanup and investigation. Require verified cache cleanup or a clean, managed cohort with demonstrably new inspections. Deny untracked clients access to pilot records server-side. An interrupted conversion resumes before the app advertises offline readiness.

## Milestones, dependencies and exit criteria

| Milestone | Depends on | Acceptance criteria |
| --- | --- | --- |
| 1. Agree contracts and qualify devices | Decisions above | Operations walks through delayed acceptance and revocation. Security signs off on removal evidence. Two real-device exercises demonstrate recoverable offline capture at the agreed photo size and complete cleanup of a prepared copy. |
| 2. Establish the server baseline | 1 | Repeat backfill during a web edit with no version regression. Demonstrate stale-write rejection, one audit event per committed operation on replay, and serialization of download grants against acceptance. |
| 3. Deliver local preparation and capture | 1 and the snapshot contract in 2 | Upgrade a populated cache, interrupt the upgrade and resume. In airplane mode reopen a prepared job, edit a note, capture 40 photos and sign. Kill the app after each saved indicator and recover the displayed work. |
| 4. Complete synchronization and review | 2 and 3 | Under a flapping connection, lose a response after commit and resume a partial photo upload. Deliver exactly one signed submission with matching hashes. Race web edits against tablet edits and verify automatic merges, explicit conflicts and re-signing. |
| 5. Prove release and recovery | 2–4 | With two registered tablets, power one off across the 24-hour boundary. Acceptance remains pending. After both verified releases, commit acceptance and independently inspect storage and audit evidence. Repeat with a crash between erasure and acknowledgment and with an attempted concurrent download. |
| 6. Pilot and expand by cohort | 1–5 and rollback rehearsal | Enroll designated inspectors and supervisors behind server-side cohort flags. Observe full visits, conflicts, acceptance and release on representative devices. Expand only after field and regulatory owners review the gates below. |

## Verification, monitoring and rollback

Automate state-transition and API contract tests for local save, receipt replay, authorization changes, stale versions, schema drift, signature invalidation and terminal acceptance. Cut the network immediately after an ordinary online open and again just after typing a note. Check the saved indicator against what survives a restart. Inject failures at SQLite commit, media rename, server commit, upload finalization and purge acknowledgment. On managed hardware test low storage, 0/40/41 photos, two concurrent additions at the limit, sign-out, interrupted download, app upgrade, reboot, clock changes, lost tablet and background suspension. Check that revoked access prevents ordinary downloads and that recovery preserves the audit trail. Reconstruct a signed inspection from server history and compare it with the tablet review copy.

Track readiness failures, oldest unacknowledged edit, upload retries and bytes remaining, conflict age, submission failures, acceptance wait by open grant, and removal evidence for every accepted inspection. A disconnected tablet's queue age is only known as of last contact. Report that timestamp. Keep customer content out of telemetry. Give support a view of blocked jobs, owning role and next action. Alert immediately on an accepted inspection with missing release evidence, duplicate committed submissions or a confirmed lost saved edit.

Start with internal managed tablets, then a field cohort with named support, then progressively wider cohorts. Compare time to prepare, sync after reconnect and accept against agreed operational tolerances from the internal trial. Require zero lost acknowledged saves, zero duplicate submissions and complete audit and release evidence for every pilot acceptance. Investigate a failed integrity or removal gate before further enrollment.

For rollback, disable new enrollment and offline downloads server-side. Keep the upgraded reader, sync, review, purge and acknowledgment endpoints available for existing grants. Let queued tablets reconnect and drain with visible receipts. If a writer corrupts data, pause that writer, preserve encrypted pending work and use the reviewed recovery path. Keep the acceptance guard active. Restore online-only operation per inspection after outstanding work is reconciled and copies are released. Rehearse rollback with one tablet offline and another mid-upload. Retire additive schemas and protocol support only after the grant and receipt inventory shows that recovery is complete.
