# Containment and corrective actions

## Immediate containment

| Priority and action | Owner role | Verification | Rollback considerations |
| --- | --- | --- | --- |
| **P0. Keep `tenant_retry_policy` disabled in eu-west and pause rollout expansion.** Confirm the effective flag state in every worker pool and keep the API on the rolled-back release during stabilization. | Incident commander and release engineer | Workers report the flag disabled. Retried jobs show delayed attempts, retry-budget exhaustion declines, queue age and depth trend down, and checkout latency returns to baseline. | If a flag change leaves pools on mixed settings, reapply the disabled state and drain or refresh affected pools gradually. Keep the flag disabled if the API must be redeployed. |
| **P0. Stabilize database load while draining the queue.** Pause further worker scale-up. If pool waits remain high, reduce worker concurrency in stages, watching throughput and connection headroom. | Queue on-call and database on-call | Database slots remain available, pool wait time falls, and completions outpace arrivals while oldest-job age declines. | If a reduction materially slows the drain while database headroom remains healthy, restore the last stable concurrency in small steps. |
| **P0. Reconcile jobs that exhausted their retry budgets.** Identify terminal or stranded jobs and replay only jobs eligible for safe retry after confirming their recorded outcomes. | Queue operations lead and checkout service owner | Reconcile affected job IDs with terminal states and checkout outcomes. Track replay success and duplicate side effects. | Stop replay if duplicate effects appear or database pressure rises. Resume from the last verified job checkpoint after reconciliation. |

## Prioritized corrective actions

| Priority and action | Owner role | Verification | Rollback considerations |
| --- | --- | --- | --- |
| **P1. Validate tenant retry policies at configuration and worker evaluation.** Ensure absent, blank, or invalid policies use a safe, bounded default. Cover cached settings and flag changes, and emit the effective delay and fallback reason. | Worker service owner | Reproduce the observed symptoms with representative configuration in testing. Verify that absent, blank, and invalid policies use the existing exponential default with bounded attempts, including when the flag changes. Verify valid tenant overrides. | Disable the flag before reverting worker code or configuration changes, and confirm the default delay remains effective across pools. |
| **P1. Limit retry and connection amplification.** Define a shared database connection budget across workers and API clients, cap worker concurrency within it, and validate how autoscaling behaves when workers are blocked on the database. | Queue platform owner and database owner | Under a retry-heavy backlog, verify connection headroom, bounded pool waits, and sustained completions. Verify that a scale-up cannot consume the API’s connection budget. | Revert limits individually to the last validated values if completions fall or pool waits rise. Keep capacity changes incremental. |
| **P2. Gate flag expansion on cohort-level health.** Canary changes on a small tenant cohort, and monitor zero-delay retries, budget exhaustion, pool wait, oldest-job age, and checkout latency by region and flag state. Document flag disable and verify worker adoption during drills. | Release engineering owner and reliability engineering lead | A canary exercise detects retry regressions and pauses expansion. A flag-disable drill confirms that all worker pools adopt the change within the agreed recovery target. | Halt expansion and disable the flag if health thresholds are crossed. Restore the previous monitoring configuration if rollout gating itself malfunctions, and keep expansion paused until the signals are reliable. |
