Receiving Orbit Webhooks

This guide covers how to verify, acknowledge, and process Orbit webhook deliveries. Statements are labelled:

  • Guarantee: current delivery behavior you can build on.
  • Recommendation: our advice. Orbit does not enforce it.
  • Unconfirmed: an open question. Don't depend on either answer.

The request

Guarantee. Each delivery is a POST with a JSON body of at most 512 KiB, carrying these headers:

Header Contents
X-Orbit-Event Event ID. Retries and manual replays of an event reuse it.
X-Orbit-Type Event type
X-Orbit-Timestamp Unix time in seconds, part of the signed content
X-Orbit-Signature v1=<hex>: an HMAC-SHA256 signature
User-Agent Orbit-Hooks/2

Recommendation. Every layer in front of your handler (load balancer, proxy, framework) should accept bodies of at least 512 KiB. Don't treat User-Agent as authentication.

Verifying the signature

Guarantee. Orbit computes HMAC-SHA256 using your endpoint's signing secret over:

<X-Orbit-Timestamp value> + "." + <raw request body bytes>

It sends the hex digest as X-Orbit-Signature: v1=<hex>.

Conflicting older documentation. Documentation from the previous system says the signature covers the parsed JSON. That is out of date. Re-serializing JSON changes key order and whitespace, so verification will fail.

A minimal verifier in Python, using only the standard library:

import hashlib
import hmac

def verify_orbit_signature(raw_body: bytes, headers, secrets: list[str]) -> bool:
    """headers: a case-insensitive mapping. secrets: every currently valid secret."""
    timestamp = headers.get("X-Orbit-Timestamp", "")
    signature = headers.get("X-Orbit-Signature", "")
    if not timestamp or not signature.startswith("v1="):
        return False
    received = signature[3:].strip().lower().encode("utf-8")
    signed = timestamp.encode("utf-8") + b"." + raw_body
    for secret in secrets:
        expected = hmac.new(secret.encode("utf-8"), signed, hashlib.sha256).hexdigest()
        if hmac.compare_digest(expected.encode("ascii"), received):  # constant-time
            return True
    return False

Recommendations:

  • Read the raw body before any JSON middleware runs, and verify before you act on the payload.
  • Compare in constant time, never with ==.
  • Reject failures with 401. That status isn't retried, so alert on failures: a wrong secret silently drops events until you replay them.
  • Never log the secret or the signature header.

Unconfirmed: timestamp freshness. Whether retries and replays get a fresh timestamp is unconfirmed. Retries can arrive about 15 hours after the first attempt and replays up to 7 days later, so a short freshness window could reject legitimate deliveries permanently. Until Orbit confirms, log timestamp age instead of rejecting on it. X-Orbit-Event is not signed, so event-ID deduplication alone won't stop a captured request being replayed.

Responding

Guarantee. Return any 2xx status within 10 seconds. Orbit ignores the response body.

Recommendation. Verify the signature, store or enqueue the event, return 200, and then process it asynchronously. Slow inline processing causes timeouts and duplicates.

Ordering and idempotency

Guarantees:

  • Duplicates are possible.
  • Order is not guaranteed. Deliveries usually arrive in the order the events were created, but concurrent retries can reorder them.

Recommendations:

  • Deduplicate on the event ID. Keep processed IDs for longer than the 7-day replay window.
  • Record an ID only after processing succeeds, ideally in the same transaction as your side effects, so a failed delivery can still be retried or replayed.
  • Replays reuse the event ID, so deduplication skips already-processed events. To reprocess one deliberately, clear its record first.
  • Don't infer order from arrival time or from X-Orbit-Timestamp. Whether it reflects event creation or signing time is unconfirmed. Check your own current state before applying a change.

Rotating the signing secret

Guarantees:

  • A secret is displayed only once. Copy it to your secret store immediately.
  • After you rotate, the new secret (labelled current) and the old one (previous) are both valid for 24 hours.

  1. Rotate in the dashboard and store the new secret.
  2. Deploy immediately with both secrets in secrets.
  3. Confirm that deliveries verify.
  4. After 24 hours, remove the previous secret.

Replay any deliveries rejected between steps 1 and 2.

Operations

This minimal Python example uses only the standard library. Supply the unchanged timestamp and signature header values, the raw body, and the exact secret bytes from secure configuration:

import hashlib
import hmac
import re


def verify(raw_body: bytes, timestamp: str, signature: str,
           secrets: tuple[bytes, ...]) -> bool:
    if not re.fullmatch(r"[0-9]+", timestamp):
        return False
    match = re.fullmatch(r"v1=([0-9a-fA-F]{64})", signature)
    if match is None:
        return False

    supplied = bytes.fromhex(match.group(1))
    message = timestamp.encode("ascii") + b"." + raw_body
    valid = False
    for secret in secrets:
        expected = hmac.new(secret, message, hashlib.sha256).digest()
        valid |= hmac.compare_digest(expected, supplied)
    return valid

Verifying the signature

The signature is HMAC-SHA-256 over X-Orbit-Timestamp + . + the raw request body, hex-encoded and prefixed with v1=.

Stale documentation warning. Older docs say Orbit signs the parsed JSON object. That is wrong for the current implementation. Signing covers raw bytes, so re-serialization, key reordering, or whitespace changes introduced by your framework will break verification.

Guarantees

  • The signed material is timestamp + "." + raw body.
  • Secrets are shown once at creation and cannot be retrieved later.
  • The service compares signatures in constant time.

Recommendations

  • Verify the raw bytes, before parsing JSON.
  • Use a constant-time comparison; never == the hex string.
  • Reject timestamps far from your clock (a few minutes of tolerance is typical) to limit replay of captured requests.
  • Accept either secret while rotating.
  • Never log the secret or full payloads, which may contain customer data. Log X-Orbit-Event and X-Orbit-Type instead.
import crypto from "node:crypto";

const secret = process.env.ORBIT_WEBHOOK_SECRET; // shown once at creation

// rawBody must be the untouched request body (Buffer or string), captured
// before any JSON parsing or body-transform middleware runs.
export function verifySignature(headers, rawBody) {
  const timestamp = headers["x-orbit-timestamp"];
  const signature = headers["x-orbit-signature"];
  if (!timestamp || !signature) return false;

  const expected =
    "v1=" +
    crypto
      .createHmac("sha256", secret)
      .update(`${timestamp}.${rawBody}`)
      .digest("hex");

  const a = Buffer.from(expected);
  const b = Buffer.from(signature);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

1. Verifying a signature (start here)

Every delivery carries:

Header Meaning

X-Orbit-Type Event type, e.g. invoice.paid
X-Orbit-Timestamp Unix seconds when the request was signed
X-Orbit-Signature v1=<hex> HMAC-SHA256 signature

The signature is HMAC-SHA256 over the raw request bytes, not over reparsed JSON. The signing string is <X-Orbit-Timestamp> + "." + <raw body>.

Your body parser must therefore preserve the raw payload before any JSON decoding. Most frameworks (express.json(), ASP.NET model binding) replace the raw stream; capture it first (e.g. express.raw({ type: "application/json" })) or verification will fail intermittently.

import crypto from "node:crypto";

const MAX_SKEW_SECONDS = 300; // recommended, not a service-enforced limit

// secrets: array of currently valid secrets (see "Key rotation")
export function verifyOrbitSignature(rawBody, headers, secrets) {
  const timestamp = headers["x-orbit-timestamp"];
  const signature = headers["x-orbit-signature"];
  if (!timestamp || !signature) return false;

  const age = Math.abs(Math.floor(Date.now() / 1000) - Number(timestamp));
  if (!Number.isFinite(age) || age > MAX_SKEW_SECONDS) return false; // replay guard

  return secrets.some((secret) => {
    const expected =
      "v1=" +
      crypto
        .createHmac("sha256", secret)
        .update(`${timestamp}.${rawBody}`)
        .digest("hex");
    const a = Buffer.from(expected, "utf8");
    const b = Buffer.from(signature, "utf8");
    return a.length === b.length && crypto.timingSafeEqual(a, b);
  });
}

Header Value

X-Orbit-Signature Signature, format v1=<hex>
User-Agent Orbit-Hooks/2
Content-Type application/json

The body is JSON and will not exceed 512 KiB.

Verifying signatures

The signature is HMAC-SHA256, computed over the signing string — the X-Orbit-Timestamp value, a literal ., then the raw request body exactly as received — hex-encoded and prefixed with v1=.

Minimal example (Python):

import hashlib, hmac

def verify(headers, raw_body, secret):
    signing_string = f'{headers["X-Orbit-Timestamp"]}.'.encode() + raw_body
    expected = hmac.new(secret.encode(), signing_string, hashlib.sha256).hexdigest()
    return hmac.compare_digest(headers["X-Orbit-Signature"], f"v1={expected}")

Rules:

  • Hash the raw bytes as received. Never parse the JSON and re-serialize it before hashing; different key order or whitespace breaks verification.
  • Compare in constant time, as above, to avoid timing leaks.
  • Reject requests whose signature header is missing or malformed.
  • Never log the signing secret or full request payloads. Log the event ID and type instead.

  • the connection times out — your endpoint has 10 seconds to respond;
  • a network error occurs; or

Receiving Orbit Webhooks

Orbit delivers event notifications to your endpoint as HTTP POST requests with a JSON body. This guide covers how to verify deliveries, what delivery behavior is guaranteed, and how to operate a robust receiver. Throughout, guarantees describe behavior the service commits to; recommendations are operational advice you should follow but that the service does not enforce.

Delivery format

Each delivery is a POST with these headers:

Header Meaning
X-Orbit-Event Unique event ID. Stable across retries and replays.
X-Orbit-Type Event type (e.g., invoice.paid).
X-Orbit-Timestamp Unix seconds when the delivery was signed.
X-Orbit-Signature v1=<hex> — HMAC-SHA-256 signature (see below).

Requests are sent with User-Agent: Orbit-Hooks/2. Payloads are capped at 512 KiB.

Verifying signatures (guarantee)

Orbit signs every delivery with the endpoint secret shown to you once in the dashboard. The signed content is:

<X-Orbit-Timestamp> + "." + <raw request body bytes>

Compute HMAC-SHA-256 over that exact string with your secret, hex-encode it, and compare it against the <hex> value in X-Orbit-Signature (after the v1= prefix) using a constant-time comparison.

Two details matter:

  1. Sign the raw bytes, not parsed JSON. Re-serializing a parsed body changes whitespace and key order and will produce mismatches. (Older documentation described signing the parsed JSON; that guidance is stale — the current implementation signs timestamp + "." + raw body as above.)
  2. Check the timestamp (recommendation): reject deliveries whose X-Orbit-Timestamp is more than a few minutes old to limit replay windows. Since the timestamp is part of the signed content, an attacker cannot alter it without invalidating the signature.

Minimal verification example (Python/Flask)

import hashlib, hmac, time
from flask import Flask, request, abort

app = Flask(__name__)
SECRET = b"whsec_..."          # store in a secret manager, never in code
MAX_SKEW = 300                  # 5 minutes

@app.post("/webhooks/orbit")
def orbit_hook():
    ts = request.headers.get("X-Orbit-Timestamp", "")
    sig = request.headers.get("X-Orbit-Signature", "")
    body = request.get_data()   # raw bytes — do not parse first

    expected = "v1=" + hmac.new(
        SECRET, f"{ts}.".encode() + body, hashlib.sha256
    ).hexdigest()

    if not hmac.compare_digest(expected, sig):
        abort(401)
    if abs(time.time() - int(ts)) > MAX_SKEW:
        abort(401)

    event_id = request.headers["X-Orbit-Event"]
    # ... enqueue / process idempotently (see below) ...
    return "", 204

Recommendation: never log your signing secret or full payloads containing sensitive data. Log the event ID and type instead.

Responding and retries

Your endpoint has 10 seconds to respond with any 2xx status. The response body is ignored, so return quickly (a bare 204 is fine) and process the event asynchronously.

What is retried (guarantee)

Orbit retries a delivery when your endpoint:

  • times out or fails at the network level (connection refused, reset, DNS), or
  • returns 408, 425, 429, or any 5xx status.

Other 4xx statuses are not retried — they are treated as permanent rejections. If your endpoint cannot accept a class of events, return a non-retryable 4xx deliberately rather than letting the delivery retry to exhaustion.

There are five retries after the initial attempt (six attempts total), on an approximate schedule of 1 minute, 5 minutes, 30 minutes, 2 hours, and 12 hours after the previous attempt. Treat these intervals as approximate; do not build logic that depends on exact timing.

Ordering, duplicates, and idempotency

  • Duplicates are possible. At-least-once delivery plus retries means the same event can arrive more than once.
  • Order is not guaranteed. Delivery usually follows event creation order, but concurrent retries can reorder events.

Recommendation: make your handler idempotent. Before processing, check whether you have already processed the X-Orbit-Event ID; store processed IDs (e.g., in a database table or cache) and skip duplicates. Where ordering matters, use a monotonic field inside the payload (such as an updated-at timestamp or version) to discard stale events rather than assuming arrival order is authoritative.

Secret rotation

Orbit supports zero-downtime rotation: two secrets are valid at the same time for 24 hours, labeled current and previous in the dashboard. To rotate:

  1. Generate a new secret in the dashboard. The old secret remains valid as previous for 24 hours.
  2. Update your receiver to accept signatures from both secrets during the overlap (try the new secret first, fall back to the old).
  3. After the 24-hour window, remove the old secret from your configuration.

Replays

The dashboard replay UI can resend any event for up to 7 days. Replays use the same event ID as the original delivery, so the idempotency check above also protects you from accidental reprocessing of replays — or, if you want replays to reprocess, you can distinguish them operationally by forcing a reprocess of a known ID rather than by trusting that replays look different.

Operational recommendations

  • Return 2xx within 10 seconds; offload work to a queue.
  • Monitor your 4xx/5xx rates; sustained 5xx burns through the retry schedule and events are dropped after the final attempt.
  • Alert on signature-verification failures — they indicate a wrong secret or possible tampering.
  • Serve a stable, publicly reachable HTTPS URL. Whether Orbit follows HTTP redirects (3xx) is unconfirmed; do not rely on redirects. If your URL changes, update the endpoint configuration in the dashboard instead.

2. Guarantees vs. Recommendations

Service Guarantees

  • At-least-once delivery: Every event is delivered at least once unless permanently dropped by a non-retryable response.
  • 10-second response window: Receivers have 10 seconds to respond before Orbit times out and retries.
  • 2xx acceptance: Any HTTP 2xx status code is treated as success. The response body is ignored.
  • 24-hour dual-secret validity: During rotation, both current and previous secrets remain valid for 24 hours.
  • 7-day replay window: Events can be manually resent via the Orbit UI for 7 days with their original X-Orbit-Event ID.

Recommendations

  • Idempotency: Treat X-Orbit-Event as an idempotency key to prevent processing duplicates.
  • Unordered handling: Delivery order is not guaranteed; concurrent retries can invert delivery sequence.
  • Immediate acknowledgement: Return 200 OK or 202 Accepted immediately and process work asynchronously in a queue.
  • Replay prevention: Reject requests whose X-Orbit-Timestamp differs from system time by more than 5 minutes.
  • Log sanitization: Never log webhook secrets or full raw payloads containing sensitive data.

3. Signature Verification

Orbit signs payloads using HMAC SHA-256 to ensure authenticity.

Algorithm

The signature is generated over the timestamp, a dot, and the raw payload bytes: $$\text{HMAC-SHA256}(\text{secret}, \text{timestamp} + \text{"."} + \text{raw_body})$$

Doc Conflict Note: Older documentation referenced signing parsed JSON. This is obsolete. Verify signatures using raw request bytes; parsing JSON alters whitespace and key order, causing verification to fail.

Minimal Verification Example (Node.js)

const crypto = require('crypto');

function verifyOrbitWebhook(rawBody, headers, secrets, toleranceSec = 300) {
  const sig = headers['x-orbit-signature'];
  const ts = parseInt(headers['x-orbit-timestamp'], 10);
  if (!sig || !ts || Math.abs(Math.floor(Date.now() / 1000) - ts) > toleranceSec) {
    return false;
  }
  if (!sig.startsWith('v1=')) return false;
  const provided = Buffer.from(sig.slice(3), 'utf8');
  const payload = Buffer.concat([Buffer.from(`${ts}.`), Buffer.from(rawBody)]);
  const keys = Array.isArray(secrets) ? secrets : [secrets];

  return keys.some(key => {
    const expected = Buffer.from(
      crypto.createHmac('sha256', key).update(payload).digest('hex'),
      'utf8'
    );
    return expected.length === provided.length && crypto.timingSafeEqual(expected, provided);
  });
}

Orbit implements an automated stepped retry policy when deliveries fail or exceed the 10-second timeout.

Retry Triggers

  • Retried: Connection timeouts, network errors, HTTP 408, 425, 429, and all 5xx statuses.
  • Never Retried: Other 4xx statuses (400, 401, 403, 404, 422). Unhandled client errors permanently drop the webhook.

Orbit makes 1 initial attempt and up to 5 retries (6 total attempts) spaced approximately:

  1. Initial: Immediate
  2. Retry 1: ~1 minute
  3. Retry 2: ~5 minutes
  4. Retry 3: ~30 minutes
  5. Retry 4: ~2 hours
  6. Retry 5: ~12 hours

  • Duplicates: Network interruptions during delivery acknowledgments can trigger retries for already processed events.
  • Ordering: Delivery order usually follows creation, but concurrent retries mean chronological ordering is not guaranteed.

  1. Store processed X-Orbit-Event IDs in a transactional database or cache.
  2. If an event ID was already processed, return 200 OK and ignore the payload.
  3. Use domain entity timestamps or sequence numbers to ignore older updates arriving after newer ones.

Orbit signs each request with HMAC-SHA256 over the message timestamp + "." + raw body, where timestamp is the string value of X-Orbit-Timestamp (Unix seconds) and raw body is the exact request body, byte for byte.

Guarantee: the signature is computed over the raw body bytes. Verify the signature before parsing or re-serializing the JSON, since reformatting changes the bytes and breaks the check. Use a constant-time comparison to avoid timing leaks.

A minimal verification example in Python:

import hashlib
import hmac

def verify(raw_body: bytes, signature: str, timestamp: str, secret: str) -> bool:
    message = timestamp.encode() + b"." + raw_body
    expected = "v1=" + hmac.new(secret.encode(), message, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)

Connect this to your framework by reading the raw request body as bytes and passing the timestamp header unchanged. In the example, secret must match the signing secret shown by our dashboard.

Guarantee: your endpoint has 10 seconds to return any 2xx status. The response body is ignored, so return a minimal 200 OK once the event is committed.

Unconfirmed: whether deliveries follow HTTP redirects. Do not rely on redirect responses for delivery; if your endpoint must move, update the configured URL instead.

Ordering and idempotency

    • Payloads are signed with HMAC-SHA256 computed over ${timestamp}.${rawBody}.

2. Signature Verification

Requests are signed using a shared secret generated in the Orbit dashboard. The secret is revealed only once; store it in a secure secret store.

Canonical Signing Format

Signatures are computed as HMAC-SHA256 over:

canonical_string = `${X-Orbit-Timestamp}.${raw_request_body}`

Legacy Documentation Conflict: Older documentation suggested signing parsed JSON. This is obsolete. The active dispatcher computes signatures over exact, unparsed request bytes preceded by ${timestamp}.. Capture raw request bytes before JSON body parsers alter formatting, key order, or whitespace.

Verification Example (Node.js)

const crypto = require('crypto');

function verifyOrbitWebhook(rawBody, signatureHeader, timestampHeader, secret, toleranceSec = 300) {
  const timestamp = parseInt(timestampHeader, 10);
  if (Number.isNaN(timestamp) || Math.abs(Math.floor(Date.now() / 1000) - timestamp) > toleranceSec) {
    throw new Error('Timestamp outside tolerance window');
  }

  const [version, expectedSig] = (signatureHeader || '').split('=');
  if (version !== 'v1' || !expectedSig) {
    throw new Error('Invalid signature format');
  }

  const hmac = crypto.createHmac('sha256', secret);
  hmac.update(`${timestamp}.`);
  hmac.update(rawBody);
  const computedSig = hmac.digest('hex');

  const expectedBuf = Buffer.from(expectedSig, 'hex');
  const computedBuf = Buffer.from(computedSig, 'hex');
  if (expectedBuf.length !== computedBuf.length || !crypto.timingSafeEqual(expectedBuf, computedBuf)) {
    throw new Error('Signature mismatch');
  }
  return true;
}

Security Warning: Never log webhook secrets or unmasked request payloads in application logs.

3. Delivery and Retry Semantics

Timeout and Acknowledgement

Endpoints must return HTTP 2xx within 10 seconds. Requests that time out, fail at the network layer, or return retryable status codes fail delivery. Response bodies are ignored.

Retry Schedule and Triggers

Orbit retries failed deliveries up to 5 times (6 attempts total) over ~14 hours:

  • Initial attempt
  • Retry 1: ~1 minute
  • Retry 2: ~5 minutes
  • Retry 3: ~30 minutes
  • Retry 4: ~2 hours
  • Retry 5: ~12 hours

Retry behavior is governed by the HTTP response:

  • Retryable: Timeouts (>10s), network errors, HTTP 408, 425, 429, and all 5xx errors.
  • Non-Retryable: Other 4xx client errors (400, 401, 403, 404, 422) immediately terminate delivery.

Pending Product Confirmation (Redirects): Security policy discourages following redirects, but dispatcher behavior on 3xx codes is unconfirmed by engineering. Do not redirect webhook endpoints; configure canonical URLs directly.

4. Ordering and Idempotency

  • At-Least-Once Delivery: Network retries can cause duplicate deliveries.
  • Out-of-Order Delivery: Events dispatch in creation order, but concurrent retries may deliver later events (e.g., order.updated) before earlier ones (e.g., order.created).
  • Idempotency Guidance: Store processed X-Orbit-Event IDs in an atomic store (e.g., relational unique index or Redis). If an ID was previously processed, return 200 OK and skip business logic.
  • Event Replays: The dashboard allows manual event replays for up to 7 days using the original X-Orbit-Event ID.

5. Secret Key Rotation

To rotate secrets without downtime:

  1. Dual-Key Window: During rotation, two keys remain valid concurrently for 24 hours, labeled Current and Previous in the dashboard.
  2. Verification Logic: Test signatures against the Current secret first. If verification fails during active rotation, test against the Previous secret. Reject requests that fail both with HTTP 401.
  3. Revocation: After 24 hours, the previous secret expires permanently.

6. Operational Advice

  • Asynchronous Ingestion: Buffer payloads into a message queue (SQS, Kafka, RabbitMQ) and acknowledge with HTTP 200 immediately to stay within the 10-second limit.
  • Payload Size Limits: Max payload size is guaranteed to be 512 KiB. Ensure proxies and web servers allow request bodies of this size.
  • Traffic Inspection: Inspect User-Agent: Orbit-Hooks/2 to identify and route webhook traffic.

Orbit Webhooks — Developer Guide

Orbit delivers event notifications to your HTTP endpoint as POST requests with a JSON body. This guide covers signature verification, delivery semantics, retries, ordering, key rotation, and operational best practices.

Endpoint requirements

  • Accept POST requests with a JSON body of up to 512 KiB.
  • Respond with any 2xx within 10 seconds. The response body is ignored; only the status code is used to mark the delivery as successful.
  • The User-Agent header is set to Orbit-Hooks/2. Allowlist it if you filter by client.

Request headers

Header Description
X-Orbit-Event Stable event id (e.g. evt_01H...). Use this as your idempotency key.
X-Orbit-Type Event type (e.g. order.created).
X-Orbit-Timestamp Unix seconds, in UTC, at signing time.
X-Orbit-Signature v1=<hex> — HMAC SHA-256 over timestamp + "." + raw_body.

⚠️ Sign the raw bytes of the request body, not a re-serialized or parsed JSON object. Our earlier integration guide stated otherwise; that note is stale. If you have a verifier built from the older guide, rebuild it against this one.

Verifying a signature

import hmac, hashlib, time

SECRET = b"<your-webhook-secret>"
TOLERANCE = 300  # seconds; recommendation, not enforced by Orbit

def verify(raw_body: bytes, sig_header: str, ts_header: str, event_id: str) -> bool:
    ts = int(ts_header)
    if abs(time.time() - ts) > TOLERANCE:
        return False  # reject stale or future-dated requests
    expected = "v1=" + hmac.new(
        SECRET, f"{ts}.".encode() + raw_body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, sig_header)

The signing secret is shown once when it is generated. Store it in your secret manager immediately — Orbit cannot retrieve it later.

Delivery and retries

After the initial attempt, Orbit retries on:

  • Network errors (DNS, connection refused, TLS handshake, read timeout).
  • A response timeout (no 2xx within 10 seconds).
  • HTTP 408, 425, 429, and any 5xx.

Other 4xx codes are treated as permanent failures — they are not retried. Your endpoint should return 2xx for any event it has durably accepted, even if business logic will skip it.

The retry schedule is approximately 1 minute, 5 minutes, 30 minutes, 2 hours, and 12 hours after the previous attempt. Five retries follow the initial try.

The schedule above is approximate. Jitter and concurrent retry workers may shift exact timings by minutes. Do not rely on a fixed wall-clock interval between attempts.

Ordering and idempotency

Delivery order usually follows event creation, but it is not guaranteed: concurrent retries mean an earlier event can arrive after a later one, and a 4xx followed by retry after a configuration change can break sequence too. Build idempotent receivers keyed on X-Orbit-Event. A retry of the same event always carries the same id, and the dashboard's replay feature reuses the original id as well.

Key rotation

You may have up to two active secrets at any time. The dashboard labels them Current and Previous. When you generate a new one, both stay valid for 24 hours, giving you a window to roll your verifier. After 24 hours, the Previous secret stops signing deliveries and may be removed.

Replay

The dashboard can resend any event from the last 7 days. Replays reuse the original X-Orbit-Event, so your idempotency key handles them exactly like a retry.

Operational advice

  • Log only event ids and types, not full bodies. Webhook payloads often contain personal or financial data.
  • Store the signing secret in a secret manager (Vault, AWS Secrets Manager, GCP Secret Manager). Never commit it.
  • Set any reverse-proxy body size cap above 512 KiB, otherwise valid Orbit deliveries will be rejected upstream.
  • Monitor 5xx and timeout rates per integration. Sudden spikes usually indicate a deploy regression on your side.
  • Return 2xx as soon as you have durably enqueued the event; do heavy work asynchronously.
  • Treat the retry schedule as approximate — design for at least 24 hours of retryable backlog.

Webhook Delivery Guide

This guide covers integrating with Orbit's webhook system. It distinguishes guarantees (contractual behaviors you can depend on) from recommendations (best practices for reliability).

Quick Verification Example

import hmac
import hashlib
import time

SECRET = "whsec_your_secret_here"  # Store securely, never log

def verify_signature(request):
    timestamp = request.headers.get("X-Orbit-Timestamp")
    event_id = request.headers.get("X-Orbit-Event")
    event_type = request.headers.get("X-Orbit-Type")
    signature = request.headers.get("X-Orbit-Signature", "")
    raw_body = request.get_data()  # Raw bytes, NOT parsed JSON

    if not all([timestamp, event_id, event_type, signature]):
        return False, "Missing required headers"

    # Reject stale requests (recommended: 5 min tolerance)
    if abs(int(timestamp) - int(time.time())) > 300:
        return False, "Timestamp out of tolerance"

    expected = f"v1={hmac.new(SECRET.encode(), f'{timestamp}.{raw_body.decode()}'.encode(), hashlib.sha256).hexdigest()}"
    return hmac.compare_digest(signature, expected), None

Note: The signature covers timestamp + "." + raw_body, not parsed JSON. An older internal note suggested signing parsed JSON; that note is stale and conflicts with the current implementation.

Delivery & Retry Semantics

Guarantees

  • Delivery attempt: POST with JSON payload (max 512 KiB)
  • Timeout: Your endpoint has 10 seconds to return any 2xx status
  • Retry triggers: Timeout, network error, 408, 425, 429, and any 5xx
  • No retry: Other 4xx responses (including 400, 401, 403, 404)
  • Retry schedule (approximate): 1 min → 5 min → 30 min → 2 hr → 12 hr
  • Total attempts: 1 initial + 5 retries = 6 attempts over ~14.5 hours
  • User-Agent: Orbit-Hooks/2

Recommendations

  • Respond 2xx quickly; offload processing to a queue
  • Return 429 with Retry-After if you need backpressure
  • Treat 425 Too Early as a transient condition (safe to retry)
  • Do not depend on exact retry timing—treat as approximate

Ordering & Idempotency

Guarantees

  • Event ID (X-Orbit-Event) is stable per event; replays reuse the same ID
  • Duplicates are possible due to retries and replays

No Guarantee

  • Design handlers to be idempotent using X-Orbit-Event
  • Store processed event IDs (with TTL ≥ 7 days to cover replay window)
  • Do not rely on X-Orbit-Timestamp for ordering; it reflects creation time, not delivery time
